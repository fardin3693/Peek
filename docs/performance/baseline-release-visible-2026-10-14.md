# Peek performance, part 2: Release + visible preview (P-PERF2)

Date: 2026-10-14. Companion to `baseline-2026-10-14.md` (P-PERF1:
Debug/offscreen). Measurement only — no application code changed, no
targets set, nothing optimized.

## 1. Conditions

Same machine and session as P-PERF1: Intel i3-4030U / 3.7 GiB RAM,
Omarchy/Arch, Hyprland on Wayland (`XDG_SESSION_TYPE=wayland`,
`WAYLAND_DISPLAY=wayland-1`), loaded desktop. Peek 0.0.1, Qt 6.11.2,
GCC 16.2.1. Both optional backends compiled in (Poppler C++ 26.08.0,
Qt Multimedia + MultimediaWidgets).

- Build: Release preset (`CMAKE_BUILD_TYPE=Release`), binary
  `build/release/peek`. Release test suite: `ctest --preset release` →
  **7/7 pass**.
- Fixtures: regenerated by the same `bench.sh` into
  `results-release/fixtures/` and verified **byte-identical** (md5) to the
  P-PERF1 fixtures: 110000 B txt, 212953 B png (1920×1080), 591 B pdf,
  88278 B wav, 145516 B mp4.
- Cache: warm only, same as P-PERF1 (no drops attempted or claimed).
  CLI N=21 (+1 warmup), preview RSS N=7 (+1 warmup, 3 s hold, SIGTERM).
  Debug and Release samples were never mixed.

- CLI startup: **no meaningful difference**. `--version` p50 differs by

Offscreen Release was 167 ms / 37424 KiB. The real session costs
**~+400 ms and ~+24 MiB**: Wayland connection, gtk3 platform theme (the

### 3b. Visible preview: three separate signals per fixture

Harness: `docs/performance/visible.sh` + `docs/performance/probe_firstpaint.cpp`.
The probe links the **unmodified** Peek sources (same list as the test
target) plus timing scaffolding only; it is compiled to `/tmp` at bench
time and is never in CMake, CTest, or the shipped binary. Fidelity notes:
probe built `-O2` vs app `-O3`; app identity (`peek`/version) set the same.

Per fixture, 1 warmup + 7 samples on the live desktop (each window lives
~1–2 s, then SIGTERM; screenshots to /tmp analyzed and deleted immediately):

- **CTOR_MS**: validator + `PreviewWindow` ctor = synchronous decode
  (text/image/PDF) or paused-control construction (media).
- **FIRST_PAINT_MS**: first `QEvent::Paint` on any widget after `show()`,
  measured in-process against the pre-spawn monotonic clock. First Qt
  paint request — not proof of photons.
- **OPENWINDOW_MS**: Hyprland socket2 `openwindow` event for the window =
  compositor mapped the surface. A mapped surface can still show an
  unfinished frame.
- **SHOT@OPEN / SHOT@+500MS**: `grim` crop of the window geometry,
  non-dominant-color fraction (stdlib PNG decode). High = varied content
  on screen; settling between the two shots shows mapping ≠ finished frame.

| Fixture | ctor p50 [range] | first-paint p50 [range] | openwindow p50 [range] | shot@open p50 | shot@+500ms p50 |
| --- | --- | --- | --- | --- | --- |
| text | 88 [74–121] | 771 [688–867] | 788 [710–895] | 0.662 | 0.474 |
| PDF | 147 [132–164] | 828 [805–898] | 840 [820–908] | 0.913 | 0.416 |
| image (1920×1080) | 283 [269–318] | 976 [932–1098] | 991 [948–1113] | 0.963 | 0.877 |
| audio | 333 [306–401] | 1017 [957–1151] | 1029 [968–1169] | 0.783 | 0.392 |
| video | 569 [522–592] | 1258 [1201–1291] | 1306 [1251–1339] | 0.613 | 0.560 |

All 35 runs produced complete samples; every screenshot decoded
(35/35 non-blank readings, content present in all +500 ms shots).

Reading the table:

- Post-decode overhead (Qt init + show + compositor map) is roughly
  constant at ~700 ms; decode cost stacks on top (text +90 → video +570).
  First paint precedes the compositor event by ~15–50 ms in every case.
- Window-mapped ≠ frame-settled: @open shots vary widely run to run
  (e.g. PDF 0.38–0.94) while @+500 ms shots are pixel-histogram-identical
  across all 7 runs of each fixture — the first mapped frame is still
  settling; half a second later it is deterministic.
- End-to-end perceived latency (spawn → mapped window) on this machine:
  **~0.8 s text/PDF, ~1.0 s image/audio, ~1.3 s video**, Release, warm cache.

### 3c. What was NOT measured (remaining uncertainty)

- Cold-cache launches: still not measured (no root, no drops claimed).
- Verified-pixels latency: no strobe in the app, so "content readable by a
  human" timing is bounded by openwindow + the shot-settling evidence
  above, not pinned to a millisecond. The P-PERF1 phone-recording manual
  procedure remains the fallback for an independent check.
- Debug visible runs: not repeated (Release is the meaningful target).
- Codec variance: one H.264/AAC file only; other codecs will differ.
- The probe is a diagnostic twin, not the binary: identical sources and
  identity, but `-O2` vs `-O3` and no install-path lookup. Any future
  discrepancy claim needs a re-run, not an assumption.

## 4. Reproduction

```sh
cmake --preset release && cmake --build --preset release
ctest --preset release            # expect 7/7
docs/performance/bench.sh --peek ./build/release/peek --outdir docs/performance/results-release
docs/performance/visible.sh --peek ./build/release/peek   # live Hyprland session; ~40 brief windows
```

`visible.sh` needs: Hyprland socket2 (`HYPRLAND_INSTANCE_SIGNATURE`),
`hyprctl`, `grim`, python3 stdlib, g++ with the same Qt6/Poppler dev files
the build uses (it reuses the exact `-mno-direct-extern-access` flag Qt's
CMake targets require — plain g++ without it fails to link). Raw CSVs:
`results-release/*.csv`, `results-visible/*.csv`.

## 5. Limitations

- One loaded i3 desktop, one Qt/Poppler/FFmpeg combination — baselines,
  not universals. Re-run on any hardware or Qt upgrade before comparing.
- Native CLI and visible runs include full session-theme cost (gtk3);
  offscreen rows exclude it. Never mix the two columns.
- The shot metric is a histogram fraction, not content recognition: it
  proves varied pixels, not correct pixels. Correctness stays with the
  functional suite (offscreen, per-provider assertions).
- Holding each preview only ~1–2 s on screen: slow-settling streams past
  +500 ms are not characterized.

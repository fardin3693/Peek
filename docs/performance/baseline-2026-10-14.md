# Peek performance baseline (P-PERF1)

> See also `baseline-release-visible-2026-10-14.md` (P-PERF2): Release
> build, Debug-vs-Release comparison, native-Wayland startup, and
> launch-to-visible-window / first-paint measurements.

Date: 2026-10-14. Status: measurement only — no preview behavior changed,
no targets set, no optimization performed.

## 1. Conditions

- Hardware: Intel i3-4030U (4 threads) @ 1.90 GHz, 3.7 GiB RAM, 7.4 GiB swap
  (~1.3 GiB available at run time; a loaded desktop, not a quiet lab machine).
- OS/session: Omarchy/Arch, Hyprland on Wayland (`XDG_SESSION_TYPE=wayland`,
  `DISPLAY=:0`, `WAYLAND_DISPLAY=wayland-1`). Benchmarks ran in a terminal
  on the live desktop, but the app ran under `QT_QPA_PLATFORM=offscreen`
  (see §4 for why).
- Build: Debug preset (`CMAKE_BUILD_TYPE=Debug`), binary
  `build/debug/peek` built 2026-10-13. Debug is for development; treat every
  number below as a Debug baseline, not a release judgment.
- App: Peek 0.0.1, Qt 6.11.2, CMake 4.4.3, GCC 16.2.1, Ninja.
- Optional backends (both present, both compiled in): Poppler C++ 26.08.0
  (`PEEK_WITH_PDF`, `libpoppler-cpp.so.3` linked) and Qt Multimedia +
  MultimediaWidgets (`PEEK_WITH_MULTIMEDIA`, FFmpeg backend installed).
- Tests: `ctest --preset debug` → 7/7 pass immediately before benchmarking.

## 3. Results (warm cache, offscreen, Debug)

Warm = page cache never dropped (no root claimed, none attempted); the first
iteration of every case is a warmup and excluded. CLI: N=21. Preview RSS: N=7
after 3 s steady hold, terminated with SIGTERM.

### 3a. CLI startup: process launch → exit (reliable, auto-measured)

Timer: `CLOCK_MONOTONIC` around fork/exec. RSS: per-process peak via
`os.wait4` `ru_maxrss` (not cumulative). The process exits by itself.

| Case | wall min | wall p50 | wall p90 | wall max | peak RSS p50 | peak RSS range |
| --- | --- | --- | --- | --- | --- | --- |
| `peek --version` | 159.0 ms | 168.0 ms | 178.0 ms | 196.3 ms | 37500 KiB | 37200–37844 KiB |
| `peek` (no args) | 203.8 ms | 226.2 ms | 237.4 ms | 261.6 ms | 39416 KiB | 38960–39876 KiB |

Notes: both cases construct `QApplication` before parsing, so this is
Qt-init-dominated startup, not argument-parsing cost. `--version` exits via
the parser (skips normal teardown); the no-arg path prints the info text and
returns normally — that, not extra work, is the likely source of the
~60 ms gap. Do not read more into the difference.

### 3b. Preview memory: live offscreen process, 3 s hold (reliable, auto-measured)

Sampled from `/proc/<pid>/status`. VmHWM = peak; VmRSS at 3 s = steady.
Wall-to-exit is the 3 s harness hold, NOT preview latency — never use it as such.

| Case | VmHWM min | VmHWM p50 | VmHWM max | VmRSS p50 (steady) |
| --- | --- | --- | --- | --- |
| text (`sample.txt`) | 50440 KiB | 50596 KiB | 50692 KiB | 50596 KiB |
| image (`sample.png`) | 61252 KiB | 61400 KiB | 61664 KiB | 61400 KiB |
| PDF (`sample.pdf`) | 62220 KiB | 62396 KiB | 62504 KiB | 62396 KiB |
| audio (`sample.wav`) | 76960 KiB | 77040 KiB | 77212 KiB | 77040 KiB |
| video (`sample.mp4`) | 81020 KiB | 81168 KiB | 81368 KiB | 81168 KiB |

Peak ≈ steady in every case (ranges < 0.5%): nothing grows during the hold.
Ordering text < image ≈ PDF < audio < video is expected — media cases carry
the FFmpeg-backed `QMediaPlayer` pipeline even while paused.

### 3c. Explicitly UNMEASURED (no fabricated numbers)

- Launch → first visible preview (pixels on screen): UNMEASURED. Peek emits
  no stdout/signal when the window maps, and offscreen maps nothing, so no
  automatic tool can observe it. Process creation, window construction, and
  visible rendering are distinct events; only the first is timed above.
- Cold-cache runs: NOT MEASURED. Cache was never dropped (requires root);
  all runs are warm. First-iteration warmup was discarded but is not a cold run.
- Release numbers: NOT MEASURED. Only the Debug configuration was built
  and tested per this task's scope; expect Release to be faster/lighter.
- Steady-state beyond 3 s / repeated open-close drift: NOT MEASURED.

## 4. Why offscreen, and what it costs

Offscreen was chosen for reproducibility: no window pops during 100+
launches, no compositor focus effects, no theme-plugin variance (empty
`QT_QPA_PLATFORMTHEME`, same as CTest). Cost: it exercises Qt init,
validation, synchronous decode, widget construction, and the media pipeline —
but not compositor mapping, vsync, or pixels on screen. Offscreen startup is
therefore a lower bound on perceived desktop startup, and offscreen RSS is
the app's own footprint without compositor-side surfaces.

## 5. Manual procedure: first visible preview (repeatable)

Use this until Peek gains an observable readiness signal (e.g. a
`--ready-fd`/`--timing` strobe — not implemented, not requested here).

1. Build Debug, pick a fixture: `P=docs/performance/results/fixtures/sample.png`.
2. Focus an empty workspace. Start a 240 fps phone recording aimed at the monitor.
3. Press Enter on `time ./build/debug/peek -- "$P"` and dismiss with Escape
   the moment the preview is readable.
4. Count frames from keypress flash to first readable preview frame;
   `latency_ms = frames / 240 * 1000`. Repeat 11×, report median + range.
5. Record the same session conditions as §1. Do not mix keyboard-to-keypress
   delay into the result; state where the clock starts.

## 6. Reproduction

```sh
cmake --preset debug && cmake --build --preset debug
ctest --preset debug            # expect 7/7
docs/performance/bench.sh       # ~3 min; raw CSVs -> docs/performance/results/
docs/performance/bench.sh --reps 11 --hold 2   # quicker variant
```

Measurement commands inside the script: `CLOCK_MONOTONIC` fork/exec timing,
`os.wait4` `ru_maxrss`, `/proc/<pid>/status` VmHWM/VmRSS sampling, SIGTERM
teardown. Tools used: bash, python3 stdlib, ffmpeg (fixtures only).
`time`/`hyperfine`/`perf`/`valgrind` are not installed here and none was needed.
No page-cache drops were performed or claimed.

## 7. Limitations

- Loaded desktop (~1.3 GiB available), Debug build, offscreen platform:
  numbers describe this baseline, not best-case or Release performance.
- Short-lived CLI RSS comes from `ru_maxrss` (whole-process peak incl. Qt
  init); allocator-level attribution (e.g. which provider holds what) needs
  a profiler, not this harness.
- Video RSS covers a paused local H.264/AAC file; codec/backend variance
  across real files is not characterized.
- The harness holds each preview exactly 3 s; slow-starting streams that take
  longer to settle would read low — check the CSVs, not just the medians.
